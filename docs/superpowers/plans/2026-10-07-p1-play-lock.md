# Play-lock fail-fast Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `startPlay` fails fast with a clear message when a locked Windows session stops Studio entering Play, and blox restores a minimised Studio window before Play and captures.

**Architecture:** A small host module (`src/studio/host.ts`) runs PowerShell from WSL or Windows: `isSessionLocked()` (LogonUI process present) and `restoreStudioWindow()` (ShowWindow SW_RESTORE on iconic RobloxStudioBeta windows). `startPlay` takes injectable probes, checks the lock before starting and when the mode never leaves Edit.

**Tech Stack:** TypeScript, node:child_process, vitest.

**Spec:** `docs/superpowers/specs/2026-10-07-ui-map-refine-design.md` §1

## Global Constraints

- No host probing on native Linux/macOS (no powershell): probes return `false`/no-op.
- Error code `play_blocked`; message starts "Windows session is locked (LogonUI is running)".
- Never throw from the probes themselves (a failing powershell = "unknown" = not locked).

## Review Focus

- powershell.exe missing or slow (> 5 s): probe must time out and report not-locked, never hang Play.
- Play already running when locked: `startPlay` must not probe or throw (alreadyRunning path).
- Studio reports "started" but mode stays Edit while unlocked: error still clear ("did not enter Play within 15 s").
- Restore with no Studio window: no-op, no error.
